Paperzilla se utiliza principalmente mediante estas superficies del producto:

- Lista de artículos del proyecto en la aplicación web
- Resúmenes por correo
- URL de fuentes RSS/Atom
- CLI (`pz`)
- Endpoint MCP (`/api/mcp`)

Esta referencia cubre los registros públicos de artículos, las fuentes RSS/Atom y MCP.

Los metadatos de los artículos pueden proceder de servidores de preprints o de literatura biomédica y clínica indexada en PubMed. Para las fuentes con seguimiento de versiones, `pdf_url` enlaza al PDF de esa versión. Si Paperzilla solo conoce un enlace general al PDF, `pdf_url` vale `null` y `publisher_pdf_url` contiene el enlace general. La página de la fuente figura en `url`. Su `url_kind` vale `revision` para una versión concreta y `publisher` para una página general.

## Consultar una versión de un artículo

Usa `GET /api/public/papers/{paper_ref}` con el UUID de un artículo de Paperzilla o su ID corto de ocho caracteres. Cuando Paperzilla conoce la versión de la fuente, la respuesta incluye `revision.source`, `revision.native_id` y `revision.version`. Por ejemplo, dos registros de medRxiv pueden compartir un DOI y tener distintos ID de artículo para v1 y v2.

Usa `GET /api/public/papers/{paper_ref}/revisions` con el ID de cualquiera de las dos versiones para ver las que Paperzilla ha registrado, empezando por la de número más alto. Cada entrada tiene su propio `paper_id`. Para enlazar a esa versión, abre su `path` en `https://paperzilla.ai`. La URL del editor puede abrir la versión más reciente.

```bash
curl -sS https://paperzilla.ai/api/public/papers/49e21baa-2b67-4997-9285-b8b8017cb24d/revisions
```

Este fragmento muestra los ID y enlaces.

```json
{
  "paper_id": "49e21baa-2b67-4997-9285-b8b8017cb24d",
  "revisions": [
    {
      "paper_id": "49e21baa-2b67-4997-9285-b8b8017cb24d",
      "version": "v2",
      "path": "/p/49e21baa-2b67-4997-9285-b8b8017cb24d"
    },
    {
      "paper_id": "af429483-f897-4696-a3e8-6c6ed6c0da5f",
      "version": "v1",
      "path": "/p/af429483-f897-4696-a3e8-6c6ed6c0da5f"
    }
  ]
}
```

### Fechas de las versiones en la salida

Ejecuta `pz paper <paper-id> --revisions` para ver las fechas de cada versión registrada. Añade `--json` para ver también la precisión y la procedencia de cada fecha. El endpoint REST público y la herramienta MCP `paper_revisions` devuelven los mismos campos en cada entrada de `revisions`.

| Columna de la CLI | Campo JSON | Significado |
| --- | --- | --- |
| `POSTED` | `posted` | Fecha en que esta versión se hizo pública por primera vez en su fuente. Úsala para decidir cuándo incluirla en una reconstrucción histórica. |
| `PUBLISHED` | `published` | Fecha de publicación de la versión definitiva en una revista o en las actas de un congreso, si se conoce. |
| `SEEN (UTC)` | `seen` | Cuándo incorporó Paperzilla esta versión o su registro al catálogo. Consulta `seen_basis` para distinguir los dos casos. |

En este ejemplo ilustrativo de ChemRxiv, la fuente solo indica el mes en que se publicó el preprint. Se desconoce la fecha de publicación en una revista, por lo que la CLI muestra `—` y los tres campos de publicación en JSON valen `null`.

```json
{
  "version": "v2",
  "paper_id": "00000000-0000-4000-8000-000000000002",
  "path": "/p/00000000-0000-4000-8000-000000000002",
  "posted": "2024-02",
  "posted_precision": "month",
  "posted_basis": "crossref-posted",
  "published": null,
  "published_precision": null,
  "published_basis": null,
  "seen": "2026-11-20T09:14:00.000000Z",
  "seen_precision": "microsecond",
  "seen_basis": "paperzilla-ingested"
}
```

Si `seen_basis` vale `paperzilla-ingested`, la fecha indica la primera incorporación confirmada de esa versión. Con `paperzilla-record-ingested`, `seen` indica cuándo se incorporó el registro identificado por `paper_id` mientras se verifica su etiqueta de versión.

Cada campo `_basis` identifica la evidencia de la fecha. Por ejemplo, `crossref-posted` indica que la fecha de publicación del preprint procede del registro de esa versión en Crossref. Cuando se conocen las fechas `posted` y `published`, su precisión es `day`, `month` o `year`. La marca temporal de incorporación en UTC incluye seis cifras decimales, por lo que `seen_precision` vale `microsecond` incluso cuando las seis cifras son cero.

`posted` y `published` conservan la precisión de la fuente con el formato `YYYY-MM-DD`, `YYYY-MM` o `YYYY`. Para una reconstrucción histórica, usa el último día del mes o el 31 de diciembre si solo se conoce el año. Por ejemplo, `2024-02` cuenta a partir del 29 de febrero. Si falta `posted`, excluye esa versión de la reconstrucción por fecha. Usa el `paper_id` de la versión elegida para solicitar su Markdown.

arXiv proporciona la fecha de envío de cada versión. bioRxiv y medRxiv facilitan la fecha de publicación del preprint. IACR ePrint ofrece un historial de versiones fechado o la fecha de aprobación inicial. Para un DOI de ChemRxiv con número de versión, Paperzilla usa la fecha de publicación del preprint en Crossref cuando el registro identifica esa versión. En PubMed, las versiones posteriores necesitan su propia fecha. La primera versión de un artículo de revista también puede usar la fecha de publicación en línea o la del número de la revista. La publicación posterior de un preprint en una revista requiere evidencia independiente. En los registros antiguos puede faltar una fecha si los datos de la fuente no permiten determinarla o conocer su precisión.

El historial puede empezar en v3 o contener v3 y v1 aunque falte v2. Paperzilla registra las versiones de arXiv, bioRxiv, medRxiv, ChemRxiv, PubMed e IACR ePrint. Para otras fuentes, la lista `revisions` está vacía. La etiqueta `unversioned` indica que Paperzilla registró una versión de ChemRxiv o IACR cuyo número se desconoce.
